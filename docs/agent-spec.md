# 智能体开发约束与规范（AI Coding Agent 治理手册）

> 适用范围：使用 Codex / Claude Code / DeepSeek（及 Cursor、Copilot、通义灵码等）等智能体进行实际项目开发时的通用约束与流程规范。
> 目标：让智能体「可预测、可验收、可回滚、可复现」，把 AI 开发的稳定性从「碰运气」变成「有流程」。

---

## 一、核心原则（5 条）

1. **验收标准先行**：写需求的同时写「怎么算完成」，没有验收标准的任务不给智能体。
2. **小步可回滚**：每次只让智能体做一件可独立验证的小事，做完即提交（git commit），坏一步能退一步。
3. **上下文显式化**：不依赖智能体「记得」，把约束、技术栈、目录结构、接口约定都写进文档或提示词里。
4. **人工在环（Human-in-the-loop）**：AI 负责「生成」，人负责「判定」，关键写入、删除、发布必须人工确认。
5. **可复现优先**：版本锁定、脚本化构建、一次命令跑通，环境问题不外溢到「AI 的锅」。

---

## 二、需求对齐（Requirement Alignment）

### 2.1 需求四件套（给智能体前必须齐全）
| 项 | 内容 | 示例 |
|---|---|---|
| 背景 | 为什么做、解决谁的什么问题 | 用户拍发票录入太慢，易出错 |
| 目标 | 一句话可验证的目标 | 拍照后 2 秒内出结构化发票字段 |
| 范围 | 做什么 / **不做什么**（边界很重要） | 只做发票/证件，不做合同 |
| 验收 | 可勾选的完成标准（见 2.2） | 见下 |

### 2.2 验收标准写法（Given-When-Then / 勾选式）
给智能体的每条需求都要带「可勾选验收清单」，避免它「自由发挥」：

```text
功能：发票 OCR 识别
- [ ] 输入一张发票图片 → 输出发票代码、号码、金额、税额、日期 5 个字段
- [ ] 金额字段格式化为 ¥1,280.00（两位小数）
- [ ] 识别置信度 < 0.6 时标记为「需人工确认」，不静默输出
- [ ] 无网络时仍可用（端侧模型）
- [ ] 单张耗时 < 2s（真机）
```

### 2.3 需求文档模板（推荐每次任务都套用）
```markdown
## 任务：<一句话标题>
### 背景/目标
### 输入 / 输出（数据结构、接口签名）
### 边界与非目标（明确不做）
### 约束（技术栈、版本、性能、兼容）
### 验收清单（勾选式，≥3 条）
### 参考（设计稿、接口文档、示例代码链接）
```

## 三、设计对齐（Design Alignment）

### 3.1 设计 Token（先定义变量，再让 AI 写 UI）
智能体写 UI 最容易跑偏的是「颜色、字号、间距、圆角」各写各的。要求它**必须先定义 token、后引用**：

```css
/* 设计 Token —— 约束智能体必须复用，禁止写死色值 */
:root {
  --primary: #2563EB;  --accent: #10B981;
  --text-main: #111827; --text-sub: #6B7280;
  --radius-sm: 8px; --radius-md: 12px;
  --space-1: 4px; --space-2: 8px; --space-3: 12px; --space-4: 16px;
  --font-base: 14px;
}
```
> 规则：**「UI 里的颜色/字号/间距必须引用 token，出现硬编码色值即判不合格」**。

### 3.2 设计对齐三步骤
1. **线框先于代码**：先给智能体看页面线框（本仓库 `设计文档/` 下的 HTML 设计图即为此用），确认布局再写实现。
2. **组件先行**：抽出通用组件（按钮、卡片、气泡、导航），AI 只允许「组装组件」，不允许每次重写样式。
3. **对照验收**：让 AI 输出后，人打开页面与设计图逐屏比对，不一致打回。

### 3.3 给智能体的「设计约束块」（直接粘进 prompt）
```text
【UI 约束】
- 主色 #6366F1，深色背景 #0F172A，圆角 14px，间距按 4/8/12/16
- 所有颜色/字号/圆角必须用设计 token，禁止硬编码
- 页面结构对照 设计文档/02-ChatFlow-UI设计图.html，逐屏实现
- 对话气泡：用户右侧主色、AI 左侧白底描边
```

## 四、任务拆解与上下文管理（稳定性核心）

### 4.1 一个任务 = 一个可验证单元
| ❌ 反例（不稳定） | ✅ 正例（稳定） |
|---|---|
| 「帮我实现整个 Agent 功能」 | 「实现 weather 工具，输入城市返回 JSON，含单元测试」 |
| 「把首页重构一下」 | 「把首页列表改成 Paging3 分页，保持现有卡片样式不变」 |

### 4.2 每条任务的「完成定义 DoD」（Definition of Done）
```text
- [ ] 编译/构建通过
- [ ] 单测通过（如适用）
- [ ] 无新增 lint 错误
- [ ] 已 git 提交，commit message 符合规范
- [ ] 运行截图/日志已附上
```

### 4.3 上下文续接（避免智能体「失忆」）
- 每个任务在 prompt 里**重述关键上下文**：技术栈、目录、当前进度、上次的接口约定。
- 维护一份 `PROJECT_CONTEXT.md`（含：技术栈、目录结构、启动命令、已完成/进行中/待办、约定），每次任务先让 AI 读它。
- 不把「脑子里的约定」当作 AI 已知信息。

## 五、编码约束（Coding Constraints）

### 5.1 技术栈锁定
```text
【技术栈锁定，不得擅自更换/升级】
- 语言/框架：Flutter 3.7.12-ohos / ArkTS / Kotlin（按项目）
- 包管理：pub / ohpm / gradle
- 状态管理：Riverpod（Flutter）
- 不得引入未列出的第三方依赖，新增依赖需先说明理由
```

### 5.2 硬性规则（违反即打回）
1. **禁止大文件覆盖式重写**：修改要「增量、局部」，保留未改动的代码。
2. **禁止硬编码密钥**：API Key 走环境变量/安全存储，提交前检查。
3. **禁止未经许可删改**：删除文件、改公共接口、改数据库 schema 必须先说明。
4. **禁止静默改变行为**：任何行为变更都要在说明里写「改了什么、为什么」。
5. **遵守现有风格**：先读项目 lint/format 配置（ESLint/ruff/clang-format 等），不另起炉灶。

### 5.3 输出格式约定
要求智能体每次输出固定结构，便于 review：
```text
## 改动说明（改了什么/为什么）
## 涉及文件（列表）
## 验证方式（怎么跑/怎么测）
## 遗留风险/未完成项
```

## 六、验收门禁（Acceptance Gates）

### 6.1 四级门禁（由低到高，逐级通过才继续）
| 级别 | 门禁 | 谁来执行 |
|---|---|---|
| L1 静态 | 编译/构建通过、lint/typecheck 零新增错误 | 自动（脚本） |
| L2 测试 | 单元/集成测试通过，覆盖率不下降 | 自动（CI） |
| L3 运行 | 真机/模拟器跑通核心链路，附截图或日志 | 人工 + 自动 |
| L4 复核 | 代码 diff 人工 review、UI 与设计图比对 | 人工 |

### 6.2 验收清单模板（每个任务收尾对照）
```markdown
## 验收单
- [ ] 需求四件套齐全，验收标准全部勾选
- [ ] L1/L2 门禁通过（附命令与结果）
- [ ] L3 运行截图/日志（真机优先）
- [ ] UI 与设计图逐屏一致
- [ ] 代码 diff 已 review，无越权/密钥/破坏性改动
- [ ] git 已提交，可一键回滚到上一个稳定点
```

## 七、稳定性保障（工程手段）

### 7.1 版本控制纪律（最重要）
- **小步提交**：一个任务 = 一个 commit，message 写「做了什么」。
- **可回滚**：每个稳定点打 tag；坏掉就 `git revert`，不让智能体「越改越乱」。
- **分支隔离**：智能体在 feature 分支干活，通过验收才合并主分支。

### 7.2 幂等与重试（智能体任务同样适用）
- 任务描述要「可重复执行」：同样的输入 → 同样的输出，不依赖「上次碰巧成功」。
- 失败重试时，明确「从哪一步重来」，而不是整体重跑。

### 7.3 多智能体协作（可选，规模化时用）
| 角色 | 职责 |
|---|---|
| 规划智能体 | 拆需求、分任务、定验收标准 |
| 编码智能体 | 只做被分配的小任务 |
| 评审智能体 | 对照规范 + 验收标准，挑毛病 |
| 主控（人或 Agent） | 调度、合并、把关 |

> 关键：**编码与评审必须分离**，自己写的代码自己不验收。

### 7.4 安全红线
1. 密钥/凭据一律不入库，用 `.env`/Keychain/DPAPI，提交前 `git diff` 检查。
2. 新增第三方依赖先做安全与许可审查，锁定版本。
3. 用户数据/PII 脱敏后再进测试环境或喂给 AI。

## 八、一句话行动清单（每次交给智能体前）

```text
1. 需求四件套 + 可勾选验收清单 已写清楚
2. 设计 token / 线框图 已提供，UI 约束已粘贴
3. 技术栈锁定 + 硬性规则 已声明
4. 任务拆成「一个可验证单元」，DoD 已列
5. 上下文（目录/进度/约定）已重述或指向 PROJECT_CONTEXT.md
6. 约定输出格式（改动说明/文件/验证/风险）
7. 准备验收门禁（编译/测试/运行/复核）
8. 干完即 commit，可回滚
```

---

## 九、针对本项目的落地（4 个项目通用）

- 每个项目仓库根目录放一份 `AGENTS.md`（或 `PROJECT_CONTEXT.md`），写入：技术栈、目录结构、启动/构建命令、设计 token、验收门禁、硬性规则。
- 设计对齐统一引用 `设计文档/0X-*.html`，作为「设计真源（source of truth）」。
- 所有 AI 生成的代码必须先过 L1/L2 门禁，再进 L3 真机验收，最后由人做 L4 复核后合并。
